# Minishell: Project Story

## The Story

Minishell started as a deceptively simple question: what does a shell actually do between the moment someone types a command and the moment a program runs? The answer turned out to involve much more than calling `execve()`. We had to build a small language processor, manage process lifetimes, route file descriptors, preserve shell state, and make the result behave consistently across ordinary commands, pipelines, redirections, signals, and grouped commands.

The project was built collaboratively for the 42 curriculum. Its history records the work of Lucca Cruz and Alex Silva, with each contributing across the parser, expansion, execution, and cleanup layers. These areas were not isolated: the team had to align their contracts as features crossed from parsing into execution and from the parent shell into child processes.

### Collaborators and Contributions

- **Lucca Cruz** focused on tokenization and parsing: splitting the input into tokens, building the command/redirection structure, and handling the execution flow. He also implemented the file-descriptor and redirection logic, the surrounding `execve()` orchestration, pipeline behavior, and the core builtin work around `cd`, `pwd`, `export`, and `exit`, including the parent/child logic that determines when a builtin runs in the shell process or in a child.
- **Alex Silva** handled the expansion and shell-language side of the project: variable expansion, quote stripping, wildcard expansion, `unset`, `env`, `echo`-related fixes, subshell lifecycle, exit-status propagation, and related signal and status fixes. The final built-in integration and cleanup were completed together near the end.

These are areas of substantial contribution visible in the repository history, not an exhaustive division of ownership. Features were integrated and debugged together.

The shell begins by keeping its own environment state and then repeatedly reads a line with GNU Readline. We check the raw input for syntax problems before changing it, then expand variables, account for wildcard patterns, split the input into tokens, parse those tokens into commands and redirections, remove syntactic quotes, and execute the resulting structure. Each stage has a different responsibility, and a mistake in an early stage can look like an execution bug much later.

The parser represents commands as a linked sequence. A command can carry arguments, redirections, input and output descriptors, and the operator connecting it to the previous command. Pipes connect neighboring commands; `&&` and `||` decide whether later commands should run. Redirections are stored separately from arguments so execution can apply them in order. Built-ins such as `cd`, `export`, and `unset` need special treatment: when run on their own, they execute in the shell process so their changes survive. An external program, or a built-in participating in a pipeline, runs in a child process so it cannot overwrite the parent shell's state.

Heredocs made this model more tangible. The shell reads lines until it reaches the delimiter, then supplies the collected text to the command as input. A pipe is a natural way to hand that text to a later process without first creating a temporary file. Reading the heredoc in a child is a common design option: it isolates the blocking read and lets the parent coordinate interruption and continuation. In this implementation, however, `ft_exec_heredoc()` reads directly from standard input in the shell process, writes the body to a pipe, and checks for status 130 to stop after SIGINT.

### The Hardest Bug: Who Owns Each File Descriptor?

The hardest bug was not just “a bad `dup2`.” It was understanding which process owned each open descriptor, which process was allowed to change standard input or output, and when each copy had to be closed. This became especially confusing around subshells because `fork()` copies the process's descriptor table. The descriptors refer to the same underlying open resources, but closing a descriptor in one process does not close the corresponding descriptor in the other. If an unnecessary pipe end remains open in a parent, child, or nested shell, a reader may never see end-of-file. If a parent-side built-in leaves a redirected standard descriptor installed, later shell commands can unexpectedly inherit that redirection.

The corresponding fix is recorded in commit [0e732d2](https://github.com/42-team-lseabra-alebarbo/minishell/commit/0e732d2), which refactored the file-descriptor backup logic and added the reset path needed around `execve()` and child execution.

The first visible failure in the redirection work was repeated `dup2` use producing a “Bad file descriptor” error or leaving the shell's standard input/output in the wrong state after a built-in. A standalone built-in runs in the parent specifically to preserve changes such as `cd`; therefore its redirection temporarily changes the actual shell process. Simply duplicating a file onto standard output is not enough: the original standard descriptor must be saved and restored when the built-in finishes. The fix added a per-command backup of the descriptor being replaced and reset it after execution. Later refactoring limited backups to parent-executed built-ins and added reset/cleanup handling in child execution to reduce “still reachable” allocations. The implementation is in [`srcs/ft_dup2_close.c`](srcs/ft_dup2_close.c), [`srcs/ft_exec_builtin.c`](srcs/ft_exec_builtin.c), and [`srcs/ft_exec_child.c`](srcs/ft_exec_child.c).

The broader subshell version of the same lesson was to close every descriptor copy that a process does not need. Child execution closes unused command descriptors, command cleanup closes redirection and pipe descriptors, and subshell cleanup releases its nested shell state. The subshell itself creates a fresh `t_data`, copies the environment, carries in the last status, then runs the normal expansion, parsing, and execution path on the contents of the parentheses. That reuse is powerful, but it means descriptor and memory cleanup must work at every nesting level.

The fix was challenging because a descriptor bug often appears far away from its cause. A command can print correctly yet leave a pipe end open; the next command hangs waiting for EOF. A redirection can work once, then break a later command because the shell's standard descriptor was never restored. A child can exit correctly while retaining memory or descriptors that only become obvious when a subshell is involved. The team had to reason about process boundaries and lifetime, not just add a close wherever an error appeared. Our test scripts helped compare combinations and catch regressions across repeated commands, redirections, pipelines, and grouped execution.

### Exit Status and Signals

Here, **shell state** means the values and resources that affect later commands: the private environment, current working directory, last exit status, and the shell's open descriptors and parsed command data. Some effects are process-wide, such as the working directory changed by a parent-side `cd`; others are stored in the shell's `t_data`, such as the environment array and last status. A child receives a process-local copy of memory when forked, so changes it makes to that memory do not update the parent shell. The shell keeps the current status in `ft_get_status()`, while `t_data.last_status` carries status into expansion and nested shell processing. `$?` expands from the last status. A successful command normally leaves status 0; a failed command propagates its relevant nonzero status, including the conventional 126/127 cases for commands that cannot be executed or cannot be found.

For a single external command, the parent waits for its child and uses `WEXITSTATUS()` when the child exited normally. A standalone built-in returns its status directly because it ran in the parent. For a pipeline, the shell records the status of the last command in the pipeline, matching the usual shell rule, and then reaps the other children so they do not remain as zombies. The code separates waiting for the last child from the cleanup wait for remaining PIDs.

SIGINT is a special case. The shell's signal handler records 130, the conventional status for interruption by Ctrl-C. The wait path avoids replacing that status with a later child result once 130 has been set. During heredoc collection, the stored status is also checked so the read can stop after an interrupt. Child processes restore the default SIGINT and SIGQUIT behavior before executing an external program, while the interactive shell installs handlers suited to its prompt and foreground-command states.

### What We Learned

We tested behavior with our own scripts, and that process changed how we think about software quality. A feature can look complete in the happy path while still failing under a slightly different combination of quoting, redirection, a pipeline, a signal, or a nested command. Finding those failures did not make the work less valuable. It showed where the model could be made stronger.

The project showed that we can do better work than we initially expect of ourselves. We studied real shell behavior, implemented meaningful features, and encountered the edge cases found in real products. A failure is not proof that the work has no value; it is information about a system that can be improved. Understanding the behavior, making a careful change, and testing its effects is how we can contribute to real software and products.

The environment uses a `char **` array of `NAME=value` strings. A more Bash-faithful design would study Bash's actual variable model and represent shell variables separately from the exported environment passed to `execve()`. That choice would affect lookup, assignment, export, unset, expansion, and process launch. It would have been a valid architectural direction to choose early, but changing to it late in this project would have meant substantial rewiring for limited practical benefit within the project's scope. The current representation is a pragmatic tradeoff, not a failure. Any redesign should be guided by Bash's real behavior and data model rather than assuming a linked list alone would make the shell more faithful.

We also tried to avoid unnecessary dynamic allocation. Heap allocation was appropriate for data whose size is determined at runtime: input and expanded strings, token and argument arrays, linked command/redirection nodes, copied or updated environment entries, wildcard match lists, nested shell contexts, and saved descriptor records when parent-side redirections are active. Fixed-size or short-lived data, such as pipe descriptor pairs and the bounded PID array, could stay in local or fixed storage. This kept allocation tied to variable-sized data and ownership that had to outlive a function, while making cleanup obligations explicit.

## Project Summary

Minishell is a compact Bash-like shell written in C for the 42 curriculum. It reads commands interactively, validates syntax, expands environment variables, tokenizes and parses input, and executes commands with built-ins, redirections, heredocs, pipelines, signals, and subshell-style groups. The bonus version adds `&&`, `||`, and wildcard expansion.

The team combined parser and syntax work, variable and wildcard expansion, interactive signal handling, subshell behavior, and process execution. The execution work included descriptor backup and restoration for parent-side built-ins, child cleanup, command-status propagation, pipeline waiting, and exit/error behavior. These contributions were integrated and tested together rather than developed as independent features.

The central lesson was that a shell is defined by the edge cases between features as much as by the features themselves. Correctness required us to understand who owns state, who owns each descriptor, which child determines a pipeline's status, and how an interruption should return control to the prompt. The project gave us a genuine view into how software is built: implement, test, learn from what happens, and improve it.
